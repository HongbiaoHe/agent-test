Canvas Agent 全链路技术架构

总览流程图

五个层次：浏览器、NestJS 接口层、BullMQ Worker、数据层、媒体支线。核心设计是唯一写入口——agent 工具与用户 REST 编辑都收敛到 CanvasService.applyOp（事务：物化表 + 操作日志 + revision），提交后经 Redis Stream 广播 canvas_patch，前端增量应用到 React Flow 投影。

03

队列与 Worker：会话状态机

独立队列 canvas-run，job 有三种 kind：run（新目标）、resume（中断续跑）、timeout（提问超时兜底）。Worker 配置为长跑设计：concurrency: 5, lockDuration: 300000（canvas.processor.ts:43），BullMQ 活跃期间自动续锁，小时级 job 不会被误判 stalled。

05

数据流转与落库

存储采用混合模型：物化表 CanvasNode/CanvasEdge 存当前态（读快），同事务追加 CanvasOp 事件日志（可回放、可审计），session.revision 即最新 op 的 seq，充当乐观并发游标。

applyOp：唯一结构写入口的事务

冲突模型的四条规则

运行期只读

session 处于 busy 态时，服务端拒绝用户结构变更（CANVAS_BUSY，service.ts:379-381）；前端同步锁 UI——nodesDraggable/nodesConnectable/elementsSelectable 全关（flow-canvas.tsx:146-148），呼吸光晕 + 磨砂 pill 提示（flow-canvas.tsx:165-181）。agent 成为唯一写者，零写-写竞争。

空闲期乐观并发

用户编辑带 baseRevision（use-canvas.ts:200-207），不匹配 → 409 CANVAS_CONFLICT，前端 catch 后重拉快照。挡多标签页/并发用户。

位置 LWW 独立通道

拖拽是 presentation：直接 upsert x/y + 广播 move_node，不占 revision、不进 op 日志、不 409（service.ts:520-546）。前端本地先行更新，失败才重拉（use-canvas.ts:190-197）。

事件日志 + 广播兜底

每次结构变更同事务追加 CanvasOp，patch 带变更后 revision；前端若发现 revision 跳变说明漏事件，可重拉快照兜底（设计文档 §5.5）。

06

媒体生成支线

画布复用现有 media 模块，关键桥接：以 sessionId 作 conversationId 传入 createGeneration，media_update 事件天然汇入画布同一条 Redis Stream，前端零改造收到刷新信号。

07

实时推送 → 页面呈现

前端遵循「REST 基底 + socket 增量」范式：快照与历史消息经 React Query 拉取作基底，socket 事件按类型四路分发增量折叠。useCanvas（use-canvas.ts:39）是整页的状态编排中枢。

运行期视觉反馈

readOnly = busy（use-canvas.ts:215）驱动：画布四周呼吸光晕 + 「Agent 工作中 · 画布只读」磨砂 pill（flow-canvas.tsx:165-181）；新增节点以 500ms 批次窗口 fitView 聚焦（flow-canvas.tsx:82-95）。

HITL 双形态

ask_user → edit 决策把答案写进工具 args（use-canvas.ts:158-167）；clear_canvas → approve/reject 按钮，reject 带明确 message 回灌模型防「已删除」幻觉（use-canvas.ts:170-187）。
