01

总览管线

五层：浏览器、NestJS 接口层、BullMQ Worker、数据层、媒体支线。全系统只有一个结构写入口——agent 工具与用户 REST 编辑都收敛到 CanvasService.applyOp，事务里同时改物化表、追加 op 日志、自增 revision，提交后经 Redis Stream 广播 canvas_patch，前端增量应用到 React Flow 投影。

04

会话状态机

状态存在 CanvasSession.status，是「画布是否只读」的唯一判据：queued / running / waiting_approval 三态属 BUSY_STATUSEScanvas.service.ts:37，此时用户的结构写被服务端拒（agent 不受限，它就是运行者）。每一次迁移都用 updateMany + where status 做 CAS，避免与并发的 stop 抢状态。

05

一次 run 的生命周期

独立队列 canvas-run，job 三种 kind：run（新目标）/ resume（中断续跑）/ timeout（提问超时兜底）。Worker 按长跑设计：concurrency 5, lockDuration 300000canvas.processor.ts:43——BullMQ 在 job 活跃期间自动续锁，小时级任务不会被误判 stalled 重复消费。

07

唯一写入口 applyOp

六种结构 op（add_node / update_node / remove_node / add_edge / remove_edge / clear）无论来自 agent 工具还是用户 REST，都走这一条路径canvas.service.ts:417-532。三层防护叠加：进程内串行 → 事务内 revision CAS → 唯一键兜底。

各 op 的落表细节

add_edge 对 unique(sessionId, source, target) 做 upsert，重复连线幂等:632-642。

remove_node 先删两端命中的边再删节点:596-602。clear 先边后点一次清空:651-656。

update_node 每次 version++，改 x/y 也算结构变更（与 move 旁路不同）:567-581。

广播时机

stream.publish 在 serialize 之外、事务提交之后——保证前端收到 patch 时数据已落库。

patch 都带变更后 revision（move_node 除外）；revision 跳变 > 1 说明漏事件，前端可据此重拉快照兜底canvas.types.ts:210-221。

08

节点 IO 契约

节点之间流动的是类型化的输出，不是自由连线。契约以 CANVAS_NODE_IO 为权威canvas.types.ts:78-86，前端在 node-io.ts:14 镜像一份用于拖线时提前拦截，服务端在 add_edge 事务内再校验一次——前端拦不住的这里也拦。

text

入 —— · 出 text

正文非空才产出输出；无输入端口，任何指向它的连线都非法。

image_upload

入 —— · 出 image

MVP 模拟上传：content 破例存 assetPath 而非 versionId，因此暂不参与生成。

image_gen

入 text, image · 出 image

自身不带提示词——prompt 与参考图全部来自入边。

video_gen

入 text, image · 出 video

暂不收 video 输入：底层管线把参考版本按图片读盘，视频只用 refs[0] 当首帧。

连线合法性判据只有一句：source 的任一输出类型被 target 接受即可canvas.types.ts:92-98。outputs 是派生字段，由 deriveOutputs 按节点类型现算canvas.service.ts:46-68——text 看正文是否非空、image_upload 看 assetPath、生成节点看 media.status === 'done'。未就绪一律空数组，下游因此拿不到素材。

09

媒体生成支线

这是全系统最长的一条链：一次工具调用要穿过 canvas 模块、media 模块、第二条队列、Google 生成 API、本地磁盘，再经由 Redis Stream 绕回前端的快照失效。

前端为什么不解析 media_update 的 payloaduse-canvas.ts:157-161：节点的媒体字段是快照层 JOIN 出来的派生值，事件里那份状态没有权威性。收到事件只做一件事——让快照 query 失效、重拉。代价是一次多余的往返，收益是不必在两处维护同一份状态推导。

人工确认回路

三个工具会中断执行等用户，但决策集不同factory:146-152：ask_user 是 edit / reject，两个破坏性/耗配额的工具是 approve / reject。用 edit 传答案是被迫的——langchain 1.4.2 的 HITL 没有 respond 决策，于是把用户答案写进 ask_user 的 args，工具随即以「答案」为返回值执行。

13

观察与风险点

本次通读中发现的、当前不影响功能但值得留档的四处。均未改动代码。

① normalizeUpdate 每批只产出一个事件event-normalizer.ts:59-84

遍历 Object.values(data) 时首个命中即 return。若同一批更新里既有 {todos} 节点又有带 tool_calls 的 messages 节点，靠前的赢，另一个被丢弃——表现为聊天区偶尔少一张工具卡（工具本身仍会执行）。

② stream.subscribe 的默认 fromId = '0'stream.service.ts:44

默认从流最早一条重放全部历史；两个网关都靠显式传 '$' 才避免与 REST 历史重复渲染。新增调用方若忘记传，会静默重放整条流。

③ 同一 socket 上的 XREAD reader 只增不减canvas.gateway.ts:77-93

subscribed Set 只 add 不 delete，reader 的 stopped 只在 disconnect 时置真；前端清理函数也只 off 监听器、不发退订socket.ts:133-136。所以在一个长连 socket 上每浏览一块画布就多一个常驻 XREAD BLOCK 2000 循环与一条 Redis duplicate 连接，跨画布事件靠前端按 id 过滤。功能正确，长会话下是资源问题。

④ 两处过时的注释与死代码

socket.ts:139 注释仍写 decisions: [{type:'respond'}]，实际发的是 edit（use-canvas.ts:228）。canvas-chat.tsx:68 的 toolDetail 还留着 get_canvas 分支，该工具已在 canvas.tools.ts:26 移除。
